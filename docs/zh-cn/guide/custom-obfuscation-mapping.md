# 自定义混淆映射表

> 这里介绍了如何在模块内建混淆方法查找规则失效时，
> 如何通过导入混淆映射表以尝试恢复模块功能。

## 模块的混淆映射表

模块的混淆映射表用于将 Hook 逻辑中使用的逻辑名称与宿主代码中的混淆名称解耦，
使得宿主在更新之后，若宿主底层方法逻辑变化不大，仅需确保新建的混淆映射表中的方法名与当前版本一一对应，
模块便能继续正常工作。

## 本功能初衷

在对宿主新版本进行适配的过程中，大部分时间都是在根据宿主的代码逻辑调整模块内建的查找规则，
对上层的 Hook 逻辑变动较少，但是维护者承认自己无法编写出十全十美的方法查找规则以在不同的宿主版本上都能正常工作，
同时**若只是因宿主更新之后导致方法查找失败致使模块功能失效**，等待维护者亲自更新查找规则也会存在明显滞后，
功能长时间无法使用的问题。
而自定义混淆映射表正是为解决**这一情况**而生：它允许你自行补全缺失的方法对应关系，无需等待维护者更新即可快速恢复功能。

## 自定义混淆映射表的结构

以下是一个混淆映射表模板：

```json
{
  "hookInfo": {
    // 以下三个字段均为可选，用于限定配置的生效范围。
    // 强烈建议填写，若未填写将导致模块忽略该限定条件，
    // 这可能会导致模块在错误的版本上加载配置导致模块或宿主崩溃！
    "module_version_code": "<moduleVersionCode>",
    "module_version_name": "<moduleVersionName>",
    "host_version_code": "<hostVersionCode>",
    "<class_name>": {
      "class": {
        "name": "<classQualifiedName>"
      },
      "[method_name]": {
        "name": "<methodName>",
        "parameters": {
          "values": [
            // 存在重载版本时按照函数签名中的参数顺序定位模块所需方法，
            // 若列表为null，则仅按方法名匹配
            "[paramTypeQualifiedName]",
            ...
          ]
        }
      },
      "[field_name]": {
        "name": "<fieldName>"
      }
    },
    ...
  },
  // 可选，用于标识官方配置和用户自定义配置。
  // 缺失签名或者签名错误不会导致导入失败。
  "signature": "..."
}
```

> 自定义映射中的`hookInfo`会与模块内建生成的`hookInfo`以**覆盖式合并**：
> 显式填写的字段覆盖对应生成值，未填写的字段则保留内建结果不变。
>
> 例如，仅设置`hookInfo.<class_name>.<method_name>.name`、而未设置其`<parameters>.values`时，
> 合并后该方法的名称取显式填写的值，参数列表仍沿用内建生成的结果。

**注意**：自定义混淆映射表虽带有签名字段，且签名校验失败也不会导致模块拒绝加载，
但导入错误的映射表可能造成模块功能失效、甚至导致模块或宿主崩溃。
因此，若你在清除自定义混淆映射表之前导入过未经签名的混淆映射表，将自动失去向维护者提交 BUG 反馈的权利，
除非你能第一时间、明确地证明：所导入的映射表与你提交的 BUG 反馈毫无关联。
例如：

1. 导入自定义混淆映射表失败或自定义混淆映射表没有生效。
2. 导入编写正确的混淆映射表之后，模块功能依旧无法恢复。
3. 提交的 BUG 反馈所涉及的功能，并未使用你所导入自定义混淆映射表中的任何字段，即二者没有任何关联。

> 未来将支持用户向模块提交自定义混淆映射表，经维护者确认并签名后，供用户按需选择并加载。

## 自定义混淆映射表的步骤

> 若模块功能一切正常，那么你并没有加载自定义混淆映射表的必要。

1. 查看模块在宿主生命周期早期所打印出来的混淆映射表日志，确定查找失败的字段。
2. 参考模块源码中内建的混淆方法查找规则，在你所使用的宿主版本中查找实际的字段名称。
3. 导入自行编写的混淆映射表。

> 若导入成功之后，在确保自定义混淆映射表正常生效的情况下模块功能依旧无法恢复，请向维护者提供 BUG 反馈。
